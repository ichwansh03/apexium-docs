## Trace Job Sliding Window

The core innovation — solving Salesforce's 24-hour Trace Flag limit:

```
1. User creates TraceJob via API
   ↓
2. TraceJobService creates TraceFlag in Salesforce (expires in 24h)
   ↓
3. Background scheduler monitors active jobs
   ↓
4. Before expiry (e.g., at 23h) → deletes old flag → creates new flag
   ↓
5. Sliding window repeats until user cancels
   ↓
6. User cancels → flag deleted → job marked completed
```

**Key class:** `TraceJobService` in `service/impl/`

```kotlin
// Simplified flow
fun createJob(request: FrontendTraceFlagRequest): TraceJob {
    val traceFlag = traceFlagService.createTraceFlag(request)
    return traceJobRepository.save(TraceJob(...))
}

fun renewJob(job: TraceJob) {
    traceFlagService.deleteTraceFlag(job.activeTraceFlagId)
    val newFlag = traceFlagService.createTraceFlag(job.toRequest())
    job.activeTraceFlagId = newFlag.id
    traceJobRepository.save(job)
}
```

## Metadata Change Tracking

Scheduled polling detects changes in Apex classes and triggers:

```
Every 6 hours (configurable):
  ↓
1. Fetch all ApexClass/ApexTrigger from Salesforce Tooling API
   ↓
2. Compare with local database records
   ↓
3. If body changed → store snapshot in MinIO, record history entry
   ↓
4. History includes: who changed, when, old body reference
   ↓
5. Diff endpoint compares current body vs any historical snapshot
```

**Storage flow:**
- Current body → PostgreSQL `body_text` column
- Historical snapshots → MinIO (`sfdc-bucket/classes/{id}/{timestamp}`)
- Diff → fetch both bodies, compute line-by-line diff

## Log Polling & Storage

```
Every 1 minute:
  ↓
1. Query Salesforce Tooling API for new ApexLog records
   ↓
2. Filter out already-processed logs (by Salesforce ID)
   ↓
3. Store metadata in PostgreSQL (author, class, timestamp, size)
   ↓
4. Fetch full log body → compress → store in MinIO
   ↓
5. Body available via /api/sfdc/logs/{id}/body or /download
```

**Retention:** Logs older than 15 days are cleaned up daily at 6 AM.

## CLI (`apexium`)

Bash script that orchestrates the entire stack:

| Command | Action |
| --- | --- |
| `./apexium start` | Runs setup wizard (if no .env), starts Docker Compose, waits for health |
| `./apexium init` | Force re-runs wizard, overwrites Salesforce credentials |
| `./apexium stop` | `docker compose down` |
| `./apexium restart` | Stop then start |
| `./apexium logs` | `docker compose logs -f app` |
| `./apexium status` | Health check + container status |

**Setup wizard flow:**
1. Check prerequisites (Docker, Docker Compose, Java 21+)
2. Prompt for Salesforce Instance URL, Consumer Key, Consumer Secret
3. Write Salesforce config to `.env`
4. Fill infrastructure defaults (PostgreSQL, Redis, MinIO, pgAdmin)
5. Generate unique `APEXIUM_API_KEY` (openssl/rand)
6. Run `docker compose up -d --build`
7. Wait for backend health check
